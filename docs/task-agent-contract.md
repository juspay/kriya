# TaskAgent contract

## Reliability and diagnostic amendments (8 October 2026)

These additions supersede conflicting original details below; the execution, privacy and approval boundaries remain binding.

- A retryable transient commitment decision may be attempted once more, subject to the existing call/failure/wall/cancellation budgets. This is a read-only classifier retry, never an execution retry. Invalid responses and non-transient authorization failures are excluded; exhausting classification still fails closed.
- Unavailable independent completion verification emits a failed `done_gate` with `DECIDER_UNAVAILABLE`. It does not increase semantic premature-DONE accounting. Existing terminal behavior and unresolved-effect checks remain in force.
- Truly empty requirement, validation and group candidate sets retain their semantic sentinel choices; requirement/validation applicability is asked independently. Byte fitting must not remove every supplied candidate and relabel its data absent. If the smallest truthful request is oversized, refuse it before HTTP.
- `captureProbabilities` optionally retains only validated distributions and numeric diagnostics in exchanges. Invalid key sets, sums, ranges and argmax results remain invalid; the full distribution never changes the selected decision or gate thresholds.
- An explicit `TaskDecider.confidenceProfile` is closed metadata describing caller-declared confidence semantics and optional default floors. Capture and validate it at construction. Explicit existing overrides keep precedence; resume applies the maximum of saved and replacement-provider floors. Effective profile metadata is reported only when supplied. Uncalibrated profiles add `UNCALIBRATED_DECIDER`; no prefix or profile assertion establishes empirical calibration.
- `captureProgressDiagnostics` adds numeric shadow counters for an active segment only. Cosmetic text changes and repeated semantic control states are measured without changing budget counters, action offers, retries, approvals or completion evidence. These counters reset on resume; no checkpoint schema is changed.

## Continuation amendments (4 October 2026)

These additions supersede conflicting details in the original sections below.

- Code may prepare a currently offered FILL/SELECT/SET_CHECKED control from a confident prior Jev requirement judgment when the exact reference is still in the filtered candidate pool. A `planning` event identifies this as code preparation; no action Choice or its confidence is invented. Compilation, binding, budgets, cancellation, policy, approvals and strict execution remain on the normal path. Submission and purchase still require real model selection.
- Applicability and value are separate questions. `focus` is explicit untrusted control data; `matchingSuppliedInputPaths` is exact eligible reference/name evidence, never authorization. An unrelated branch does not use the speculative value confidence. Uncertain applicability is rejected through bounded retries, not cached as irrelevant. Structured candidate input paths are emitted only from actual input references, with sensitive values still hidden.
- After bounded unusable action decisions, confidently unavailable required data can yield the existing `needs_input` result once concrete preparation is exhausted. Required parent selection, expansion or navigation can still proceed first. A single confidently required ready native submitter can narrow the actual action Choice to submission, inspection, settling, scrolling and refusal; no submit is dispatched without that Choice and the existing policy gate.
- `submittedControls` records bounded observed checked states in the same-form pre-execution dispatch snapshot, including unchanged controls and explicit outcome uncertainty. It survives signed checkpoint/resume. It is not proof of persistence; final/review record or independent saved-state evidence is still required. `expected.inputPath` identifies a supplied FILL reference only after matched execution readback; sensitive contents are never exposed.
- Strong forward/reverse agreement on NONE retains its minimum confidence at the caller's unchanged floor. The supplementary binary effect judgment is used only for diffuse agreement below that floor. Concrete commitment effects are never overridden.
- A preparatory uncertain FILL can be attempted in a later authoritative authorized document only with input-only effects, a unique non-sensitive target, exact confident requirement reference, and observed absence of the required value. This exception removes only that preparation's retry barrier. Same-document, sensitive and lasting-write uncertainty remains protected.
- For deciders with `supportsRequirements`, a rejected completion proposal withholds DONE until the document, fingerprint or collected READ evidence changes. Other offered operations still require actual model selection and ordinary authorization.
- After actual form submission, visible application validation bound to an empty control can trigger `purpose: 'validation'`. This focused assessment judges whether correction belongs to the user's goal, then chooses only offered typed references or reports missing data. It neither fabricates required flags nor overrides effect uncertainty.
- Completion-only `verifiedPreparationFacts` restates actual matched supplied-input preparation and submission attempts, including possible no-op fills and uncertain submission outcomes; `preservedOriginalValueFacts` restates bounded non-sensitive KEEP_CURRENT submission-snapshot values. These typed facts never assert a real charge, serialized payload or persistence. Test-payment semantics apply only to a requested test transaction; matching resulting record evidence remains required.
- `TaskGoalRequirement.assessedAtLedgerSeq` records the actual ledger length of a judgment. Cached peripheral assessments may be reconsidered after a later successful main-form dispatch, using current observations and actual decider calls. Standalone peripheral workflows remain assessable.
- `verifiedCurrentGoalStates` restates actual satisfied checked-state requirements and current observed values, with the existing host independent-read flag. Unsatisfied requirements remain in the request; these individual matches never replace whole-goal verification or persistence gates.
- Actual non-sensitive native optgroup labels are projected as `groupLabel` / `optionGroup`, and their associations participate in semantic caches and held-target freshness. A verified applied SELECT change with `readback.changed` can re-assess cached unavailable non-sensitive SELECT siblings in the same form; text requirements, sensitive selects and other forms remain untouched.
- A malformed completion response can re-arm a proactive completion probe under existing decision-failure/call/time budgets. Invalid answers remain rejected; evidence argmax validation is not relaxed.
- Same-form submission observations can carry `preservedChecked` under an actual matching KEEP_CURRENT requirement and `selectedOption` with actual enabled observed labels and truncation. These retain evidence of preservation and comparison, not a payload/persistence claim or an exhaustive website inventory. Verified native exclusive-radio changes can trigger the same narrow unavailable SELECT sibling reassessment as native SELECT changes. Ordinary checkboxes, text requirements, sensitive controls and other forms remain outside this resampling.
- Native mutually exclusive groups use one `purpose: 'group'` judgment over observed members. Opaque `controlId` values deduplicate representations of one actual control without merging distinct controls with duplicate labels or values. Sibling unchecked requirements are derived from the selected member; code never emits unsupported native-radio uncheck commands. Group assessments are reconsidered after independent reads and resume.
- `submittedControls.preservedValue` retains an exact non-sensitive, untruncated original FILL value only under a required KEEP_CURRENT assessment that still holds in the same-form pre-execution submission observation. Its optional checked state is omitted for these text fields. This is preserved preparation context, not actual payload or persisted-state proof.
- `expected.preparationBasis: 'matched_supplied_input_submission'` is emitted only for an actual matched supplied-input FILL retired by actual submission. This is preparation/dispatch evidence, never persisted-state proof. Private values remain hidden.
- Current receipt text and relevant main passages take priority over historical page text and duplicated instructions when fitting completion requests. Read/filter and unchanged-state goals may use their rendered evidence; lasting changes still require independent persistence/result evidence. Every goal clause remains required.

- The TypeSafe decider advertises `supportsRequirements`. Before action selection, the coordinator uses argument questions with `purpose: 'requirement'` to assess final FILL, SELECT, SET_CHECKED and pressed-button states, and `purpose: 'activation'` for necessary form submissions. `KEEP_CURRENT`, `REQUIRED_UNAVAILABLE` and `NONE_APPROPRIATE` are fixed final sentinels, never rotated ahead of data candidates. A low-confidence assessment is rejected rather than cached as irrelevant. Known data can advance while missing data remains pending. The completion gate checks these requirements independently of executed postconditions.
- Requirements are cached by observed control semantics, including option labels, native required state and validation opt-out, and retained in checkpoints. Form preparation invalidates the associated activation receipt. A submission receipt identifies activation, not persistence. Resume discards unavailable assessments so supplied data can be reconsidered.
- Observed/model elements include input name, autocomplete, native input type, form ID, validation opt-out, landmark, accessible ancestor context, expansion and pressed state. Form native validation opt-outs are honored for SUBMIT and implicit Enter; server validation remains separate. Changing the validation opt-out changes the strict target signature. Initial page text and non-sensitive controls retain the starting state for comparisons.
- Candidate fitting preserves exact matches to non-sensitive supplied values and observed option codes at both candidate caps. Native option codes are model data. Sensitive candidate codes and values remain hidden. Verified numeric representations of exact English number-word goal spans are accepted; code performs the normalization and validates the source offsets. No model-generated value is accepted.
- Invalid decision/argument choices do not exclude a target or an entire operation. Actual rejected execution and uncertain-effect exclusions remain. Repeat protection scopes successful commands to the current document and fingerprint; uncertain command exclusions remain across documents. Missing protocol choices are bounded invalid decisions, not requests for user data.
- Forward/reverse concrete commitment disagreements return both classes in `alternatives`, and the coordinator requires their union of effects. A low-confidence NONE, missing classifier or unknown class continues to fail closed. Classification includes the target, form members and submitters, and nearby value-free passages.
- With confirmation enabled, `TASK_QUESTION_KEYS.commitmentPresence` asks a separate binary Choice about immediate effects in the same request. It applies only to agreement on NONE whose primary minimum confidence is below the configured floor. Strong primary agreement retains its confidence. A possible effect in the applicable fallback becomes OTHER_COMMITMENT; a concrete class from either primary judgment is preserved. Binary criteria rotate and telemetry reports the actual offset.
- Selected requirement references retain their model confidence and can be reused only if the current filtered candidate pool still offers the exact reference for the same operation. Binding, compilation, authorization and strict execution run again. Satisfied observed requirements after a lasting write may trigger an independent saved-state gate before another action judgment; every completion check remains required.
- `TaskTransport.refresh({ url, allowedOrigins }, call)` is an optional controller-side GET of the current authorized view, safe from POST resubmission. Together with authoritative `location`, it enables `freshStateObservations`. `TaskObserveRequest.freshState` binds the latest session/snapshot/document scope and origins. The host validates location before and after reading, requires the bridge to report a new document at the same URL, and consumes this flag before sending page messages. A callback merely claiming a new document is rejected. The coordinator invokes it only with NAVIGATE authorization and no caller verifier. It supplies `independentRead` to subsequent action/completion judgments until another lasting write requires fresh evidence. Other hosts still need a later document or authoritative caller verifier.
- State-change completion (`expect.answer: false`) judges every literal sentence/comma-separated clause in a batch, preserving the complete goal as context in every question. `TASK_QUESTION_KEYS.completionPartPrefix` names additional clause questions. At most eight questions are formed by combining overflow clauses, never dropping them. All operational clauses must be SATISFIED. Action-clause requests can offer `CALLER_CONTEXT_ONLY` for a personal reason or relationship containing no website action, quantity, state or constraint. The adapter composes that actual model judgment as fulfilled caller context at its original confidence; it never accepts this vocabulary for informational or unoffered requests. All remaining clauses, evidence and local gates stay required; confidence is the minimum across clause decisions. Every asked answer must be present and valid. Read-only tasks retain their whole-goal judgment. Evidence selection asks for an observed fact supporting at least one requirement; code still enforces grounding, persistence, postconditions, uncertain-effect resolution and all goal requirements.

Current acceptance results and limitations are recorded separately in [task-agent-status.md](task-agent-status.md).

## 2. Module to exported symbol to type table (what implementers code against)

Every function is exported by name (no default exports). ## 4. Pure-module semantics

### 4.1 `computeOffers(input)`

- `operations` always contains `DONE` and `BLOCKED`. A host operation is offered iff it is in `capabilities.operations` AND `allowedOperations` AND has at least one legal target (WAIT: `capabilities.waitDurationsMs` non-empty; SCROLL: see below) AND survives the capability consequences of 4.4.
- `targets[op]` lists element ids whose `operations` include `op`, minus `exclude` entries: an entry removes an element when its `targetId` equals the element id OR its `signature` equals the element signature; an entry with neither removes the whole operation. The coordinator keeps exclusions as (operation, signature) pairs and maps them to the current ids every loop (digests, repeat keys and uncertain entries outlive a snapshot, target ids do not); an uncertain page-level SCROLL is excluded with `targetId: TASK_PAGE_TARGET_ID`.
- If `observation.dialogs` contains a modal dialog, only elements whose `dialogId` belongs to a modal dialog are offered (the rest are obscured).
- SCROLL targets: `TASK_PAGE_TARGET_ID` iff `observation.page.scroll.directions` is non-empty, plus (only when `capabilities.scrollContainers`) every element offering SCROLL whose own `scroll.directions` is non-empty.
- WAIT, DONE, BLOCKED have no `targets` entry.
- Order of ids is document order (the order of `observation.elements`).

### 4.2 `compileCommand(input)` checks, in order (first failure wins)

1. `operation` in `offers.operations`, else `OPERATION_NOT_OFFERED`.
2. Target: for `TASK_TARGET_OPERATIONS` the `targetId` is required (`TARGET_REQUIRED`), in `offers.targets[operation]` (`TARGET_NOT_OFFERED`) and present in `observation.elements` (`TARGET_UNKNOWN`). SCROLL: `targetId` optional; `TASK_PAGE_TARGET_ID` means no target in the command; otherwise must be offered. WAIT: a `targetId` is `TARGET_NOT_OFFERED`.
3. Argument: `describeArgument` null and an argument given -> `ARGUMENT_UNEXPECTED`; spec non-null and none given -> `ARGUMENT_REQUIRED`; `ref.source` not in `spec.sources` -> `ARGUMENT_NOT_ALLOWED`; then per source (`ARGUMENT_INVALID` unless noted): `goal_*` text equals `goal.slice(start,end)`, non-empty text; `input` path in `inputRules`; `resolver` id in `resolvers`; `observed_option`: `ref.targetId === element.id`, option exists in `element.options` (`OPTION_UNKNOWN`), not disabled (`OPTION_DISABLED`); `protocol`: `slot` equals the spec slot, token valid for the slot: key in `capabilities.keys` (and not `Enter` when `capabilities.implicitSubmitDetection` is false), direction in the target's (or the page's) `scroll.directions` (TOP only when UP is possible, BOTTOM only when DOWN is), duration token numeric and in `capabilities.waitDurationsMs`, checked in `TASK_CHECKED_CHOICES` (radio: `CHECKED` only), `EMPTY` only for slot `value`.
   Binding and sensitivity, for slot `value` (all `ARGUMENT_NOT_ALLOWED`): (a) a `goal_*` ref, a non-sensitive `input` and a non-sensitive `resolver` are rejected when `element.sensitive` is true (a goal literal would carry a secret through every decision question; declare the data as a sensitive input instead); (b) a sensitive `input` or sensitive `resolver` is rejected unless its binding allows the element: default (no `bind`) = `element.sensitive === true` and `observation.origin` in `input.origins`; with `bind`: `requireSensitiveElement` (default true for sensitive leaves) is honored, `origins` (default `input.origins`) must contain `observation.origin`, `elementKinds` and `inputTypes`, when given, must contain the element's kind and `inputType`; (c) `EMPTY` is always allowed.
4. Build the command: `target` = `{sessionId, snapshotId, targetId, signature}` taken from the observation and the element; SET_CHECKED `checked = token === 'CHECKED'`; WAIT `durationMs = Number(token)`; PRESS `key = token`; SELECT native `optionId` from the ref and `optionLabel` from the option; FILL `value` = the ref itself.

`compileCommand` never reads input values, never classifies effects and never calls a decider. A caller `bind` with `requireSensitiveElement: false` and no `origins` is `INVALID_REQUEST` at init.

### 4.3 `buildCandidates(input)`

Order of candidates (deterministic) and ids `c1..cn` assigned after filtering and trimming. FIRST the binding and sensitivity rules of 4.2 step 3 filter the candidates for this element; every filtered candidate increments `withheld` and is never trimmed-in later. THEN the rest:

- slot `value` (FILL): `goal_literal` (quoted segments in `"` `'` backtick with offsets inside the quotes, email addresses, http(s) URLs, ISO dates, numbers), then `goal_span` (code-proposed spans: a deterministic function of the goal string alone, at most 8 spans of 1 to 120 characters, every span verifiable by offsets (`goal.slice(start, end) === text`), no stopword or phrase list tied to a site, a language or a task, no dependence on the page; owned by M1b, decision D6, and covered by `resolver.test`: determinism, offsets verify, the 8-span cap, empty and astral goals, and a source scan for site words), then one `input` candidate per scalar leaf (label `input:<path>` plus the declaration description, `preview` only if the leaf is non-sensitive, its `expose` is not `label` and `TaskCandidateInput.previews !== false`), then one `resolver` candidate per resolver whose `slots` includes `value` (label = resolver description, `sensitive` = resolver.sensitive, ref key `value:<target signature>`), then protocol `EMPTY` (label "Clear the field") when the element is not read-only. On a sensitive element only sensitive bound `input`, sensitive `resolver` and `EMPTY` remain.
- slot `option`: one `observed_option` per non-disabled option of `element.options` (label and preview = option label).
- slot `checked`: protocol `CHECKED`, `UNCHECKED` (radio: `CHECKED` only). slot `key`: `capabilities.keys` minus `Enter` when `implicitSubmitDetection` is false. slot `direction`: the offered `scroll.directions`. slot `duration`: `capabilities.waitDurationsMs` as `String(ms)`.
- If more than `limit` candidates remain, keep the best by token overlap with the target label, description, goal and input descriptions, and set `truncated: true`. Never truncate protocol enumerations below their natural size (they are small).
- Sensitive candidates never have `preview`; their `label` is path-like and library-authored.
- Empty candidate set means the coordinator skips the decider and returns `needs_input`: reason `input_not_bound` when `withheld > 0`, else `no_candidates`. The requirement description tells the caller to declare a `bind` or a sensitive input; it never names a value.

### 4.4 Capability flags and their consequences (every flag has one; a flag with no consequence is removed from the type)

`capabilities` are read at init and again after every `documentId` change (a remote host's `hello` is per document); offers are recomputed from the fresh value. A change that breaks a required flag ends the run (`failed` `HOST_INCAPABLE`).

## 5. Execution conventions

### 5.1 `toActionCommand(command, context)` mapping (M3a calls it; M1a implements the executor side of every row)

Strict precedence (three channels, one rule): the executor runs in strict mode when ANY of `ExecutionOptions.strict === true`, `ExecutionOptions.target` present or `parameters.strict === 'true'` holds, and never leaves it. ## 6. TaskAgent: state machine and loop

### 6.1 States

`INIT -> OBSERVE -> OFFER -> DECIDE -> (ARGUMENT) -> COMPILE -> CLASSIFY -> POLICY -> MATERIALIZE -> EXECUTE -> OBSERVE ...`; `DECIDE` returning DONE goes to `GATE`; `GATE` passes to `COMPLETED` or fails back to `OBSERVE`.
Terminal: `COMPLETED`, `BLOCKED`, `FAILED`, `CANCELLED`. Paused (terminal for this call, resumable): `NEEDS_INPUT`, `AWAITING_APPROVAL`. A `BLOCKED`, `FAILED` or `CANCELLED` result that leaves uncertain entries nobody resolved carries a checkpoint with `pending.kind 'uncertain_effect'` so a caller can resolve them (6.4). Every result of every status carries `lastEffect` (the effect the host reported for the newest ledger entry, `none` for an empty ledger) and `unresolvedUncertain` (ledger seqs that nothing resolved, recomputed from the ledger at result time with caller resolutions, postconditions and transitions applied); there is no `uncertain` boolean.

One boundary rule for every budget (the `TaskBudgets` doc comment says the same): a budget of N tolerates N and the (N+1)th blocks. Work counters (`steps`, `modelCalls`) are checked BEFORE starting a unit: `usage >= N` refuses the next one. Occurrence counters (all the others) are checked AFTER counting an occurrence: `usage > N` blocks. Wall time blocks when active elapsed time exceeds the limit. `steps` increments once per DECIDE that reaches the decider; `steps >= maxSteps` before a new DECIDE -> BLOCKED `BUDGET_EXHAUSTED` (`maxSteps`). `modelCalls` increments for every decider call of any stage; `modelCalls >= maxModelCalls` before a call -> BLOCKED (`maxModelCalls`). Tests assert both sides of every boundary (N tolerated, N+1 blocks).

### 6.3 Ledger rules

- Every `host.execute` outcome appends one `TaskLedgerEntry` (rejections included, for audit); `seq` is 1-based and monotonic; `observationOrdinal` is the coordinator ordinal of the observation the command was compiled against and `observationSequence` its host sequence (audit only). `startedAt` and `finishedAt` are coordinator clock values.
- `postconditions` are attached when `status` is `applied`, `noop_already_satisfied`, `navigated` or `uncertain`, or when `status` is `failed` and `effect !== 'none'`. They are derived from the command, the target element and the materialized value only (never from the readback). Operations other than FILL, SET_CHECKED and SELECT have none.
- A `navigated` outcome (realm lost with the next document confirmed, or an in-page URL change) is an executed action: it counts toward `actionsExecuted` and `mode`, never toward `uncertainEffects`. If its effect is `uncertain` it is resolved by a transition (7.2 step 2); if that effect belongs to a commitment it joins `pendingCommitments` until a postcondition or the caller resolves it.
- Caller effect resolutions (6.4) are stored on the entry as `resolution`; gate-derived resolutions are recomputed from the ledger and the latest observation each time (they are never stored on an entry, so a later observation can change an inference).
- History for the decider (`TaskHistoryEntry`) is label-only: operation, target label, a non-sensitive argument preview, status, effect, `pageChanged`, url. Sensitive arguments show `[sensitive input]`.
- Repeat key = `digest + '|' + observation fingerprint`. The digest includes the argument and is only known after the decision, so a repeat cannot be removed from the offers beforehand: a command whose repeat key already executed is rejected at compile time (history `rejected_decision`, `invalidDecisions++`) and its (operation, signature) is excluded for this fingerprint. An `uncertain` entry's (operation, signature) is excluded for the whole run; a caller `not_applied` resolution lifts it. Exclusions are stored as (operation, signature) pairs and mapped to current element ids each loop (`TaskOfferExclusion`).
- Grant accounting: every executed command that was allowed by grants calls `consumeGrants` once; the updated authorization is what later checkpoints carry.

### 6.4 Approval and resume

An approval request holds: id, random `nonce` (`createId('non')`), `digest`, `contextDigest`, the observation fingerprint, the redacted `TaskCommitContext`, `createdAt` and `expiresAt = createdAt + approvalTtlMs`, and `priorUncertain` when an earlier uncertain entry is why approval is needed.

`resume({ checkpoint, resolution, inputs?, options? })`:

1. Integrity first. `hasUnsafeKey(checkpoint)` or a malformed shape -> `CHECKPOINT_INVALID`. Verify `checkpoint.integrity`: with `options.checkpointKey` it is `hmac_sha256:` + `hmacSha256Hex(key, stableStringify(checkpoint without integrity))`; without a key it must equal `sha256:` + the SHA-256 of the same canonical text AND `checkpoint.id` must be in this agent instance's registry of issued checkpoints (at most `checkpointRegistry`, oldest evicted). Any mismatch -> `failed CHECKPOINT_INVALID`. Only after this does `checkpoint.request.authorization` count as the run's authorization (it is a signed value the agent itself produced, never a grant source a caller can edit).
2. Validate `checkpoint.version === 1` and that `pending.kind` matches `resolution.kind` (`RESOLUTION_MISMATCH`; `uncertain_effect` pairs with kind `effect`). The run keeps its `runId` and `sessionId`; `usage` continues in full: counters persist and `elapsedMs` is ACTIVE time accumulated across resumes (the clock restarts, the budget does not, so a pause/resume loop cannot bypass `maxWallTimeMs`; time spent paused is not counted). The effective options are the checkpoint's options TIGHTENED by `resume.options` (budgets: the smaller; confidence floors and `minEvidence`: the larger; `allowUncertainCompletion`, `allowUnverifiedLocation` and `allowRunLoss`: true only when both are true; `requireGroundedCompletion`: true when either is; timeouts: the smaller), so a resume never raises a limit or relaxes a guard. `consumedApprovalIds` continues.
3. Inputs = deep merge of `checkpoint.request.inputs`, `resume.inputs`, `resolution.inputs` (unsafe keys rejected); declarations merged by path. Every path in `checkpoint.request.sensitivePaths` that is missing from the merged leaves AND not listed in `resume.omitSensitivePaths` yields `needs_input` again with a `sensitive_input` requirement per path (the run does not continue with a hole). A caller who cannot or will not supply a secret lists it in `omitSensitivePaths`: the run continues without it and a command that needs it returns `needs_input` (`input_missing`) at that point, so a withheld, unneeded secret never deadlocks a resume.
4. `inputs` resolution: continue at OBSERVE.
5. `effect` resolution: `ledgerSeq` must name an unresolved uncertain entry (else `RESOLUTION_MISMATCH`). `applied` stores `resolution {by 'caller', effect 'applied'}`; `not_applied` stores `effect 'none'` and removes the entry's digest from the run's exclusions. Event `effect_resolved`. `usage.uncertainEffects` is recomputed as the number of still-unresolved non-commitment uncertain entries, so resolving the entry that blocked the run lets it continue. Continue at OBSERVE.
6. `approval` resolution, in this order, each failure refusing the resume and emitting its approval event: (a) `approvalId` in `consumedApprovalIds` -> `failed APPROVAL_CONSUMED` (event `consumed`); (b) `now > approval.expiresAt` -> `failed APPROVAL_EXPIRED` (event `expired`); (c) `approvalId`, `nonce`, `digest` and `contextDigest` must all equal `pending.approval` -> `APPROVAL_MISMATCH` (event `mismatch`). `deny` -> BLOCKED `POLICY_DENIED`. `approve` with `scope: 'run'` adds a bounded grant per commitment effect of the command for the page origin (`addRunGrants`, `maxUses = resolution.maxUses ?? TASK_DEFAULT_RUN_GRANT_USES`). Then rebind: observe; if `documentId` differs from `approval.documentId` the approval is void (event `void`) and the loop continues without it; find the element whose `signature` equals the pending target's AND whose `twins` equals the recorded `approval.command.target.twins` (exactly one such element, else void); rebuild the command against the new snapshot (SELECT native: map the option by label); recompute `commandDigest` (with the element's current href, form target, hints, sensitivity) and the `contextDigest` from the NEW observation: if either differs from the approval's the approval is void (event `void`) and the coordinator asks again with a fresh request (the page changed under the approver); otherwise `policy.evaluate` runs with `approvedOnce = { approvalId, digest, contextDigest }` and the command proceeds through MATERIALIZE and EXECUTE, where the approval is consumed before the call. A transport timeout on the resume call itself leaves the checkpoint unconsumed only if the agent never reached the consume step; a second submission after consumption is `APPROVAL_CONSUMED` (single process) or refused by `consumeApproval` (cross process) and the deterministic `requestId` lets the host or app dedupe the one command that did execute.

## 7. DONE gate and completion

### 7.1 Inputs

`TaskGateInput`: `goal`, the fresh observation `G` taken by the gate with its coordinator `observationOrdinal` and `receivedAt`, the ledger, `collected` (READ passages of the run), `expect`, the optional decider decision, the optional caller verifier result, `floors`, `minEvidence` (default 1), `allowUncertainCompletion` (default false), `requireGrounded` (default false).

### 7.2 Algorithm (`evaluateLocalGate` = steps 1-3, `evaluateFullGate` = 1-6); failures accumulate, they do not short-circuit

1. Freshness. If the ledger is non-empty: `observationOrdinal > max(entry.observationOrdinal)` and `receivedAt >= max(entry.finishedAt)` (both are coordinator values: host sequences restart per document and page clocks may skew, so neither is compared), else `NO_FRESH_OBSERVATION`.
2. Uncertain effects. For each entry with `effect === 'uncertain'` the first matching rule resolves it (`resolveUncertain`):
   a. the entry carries a caller `resolution`: resolved by `caller` with that effect;
   b. the entry has postconditions and all are `holds`: resolved by `postcondition`, `applied`; any is `violated`: resolved by `postcondition`, `none`;
   c. transition: `G.documentId !== entry.scope.documentId`, or `G.url !== entry.url`, or every postcondition of the entry is `retired`: resolved by `transition`, `applied` (an inference: the page moved on after the call; the server-side result is for the verifier to confirm);
   d. otherwise unresolved.
   Unresolved entries land in `unresolvedUncertain`; each adds `UNRESOLVED_UNCERTAIN_EFFECT` (with `ledgerSeq`) unless `allowUncertainCompletion`. Resolutions land in `resolutions` and `completion.resolvedUncertain`. A hard-navigation SUBMIT whose realm was lost therefore completes when the next page is verified, and the completion record says it was resolved by transition.
3. Postconditions. `checkPostconditions(ledger, G)`; any `violated` or `absent_violated` adds `POSTCONDITION_VIOLATED` (with `ledgerSeq` and the label as `detail`). `diverged` and `retired` add nothing: both are reported in `completion.postconditions` and shown to the verifier through `expected`.
4. Independent verification (full gate only). `decision` absent -> `DECIDER_UNAVAILABLE`. `verdict` `NOT_SATISFIED` -> `VERIFIER_NOT_SATISFIED`; `UNCERTAIN` -> `VERIFIER_UNCERTAIN`; `SATISFIED` with `confidence < floors.completion` -> `CONFIDENCE_BELOW_FLOOR`. Evidence: every cited id must be an element id of `G` or an id of `collected` (else `EVIDENCE_NOT_IN_SNAPSHOT`) and the number of valid ids must be `>= minEvidence` (else `EVIDENCE_MISSING`). Evidence from a collected passage is recorded with `source: 'collected'`, evidence from `G` with `source: 'observation'` and the control's observed `state`.
5. Answer. `expect.answer === true`: `choice` must be `YES` or `NO` with `confidence >= floors.completion`, `UNKNOWN` -> `ANSWER_UNKNOWN`, `NOT_APPLICABLE` or absent -> `ANSWER_MISSING`. `expect.answer === false`: the answer is ignored. `expect.answer` absent: `YES`/`NO` needs `confidence >= floors.completion` (else `CONFIDENCE_BELOW_FLOOR`), `UNKNOWN` -> `ANSWER_UNKNOWN`, `NOT_APPLICABLE` or absent -> no answer.
6. Caller verifier. `NOT_SATISFIED` or `UNCERTAIN` -> `CALLER_VERIFIER_REJECTED` (authoritative veto). `SATISFIED` alone never completes (the verdict vocabulary is the model's `TaskCompletionVerdict`). With `requireGrounded` and `basis === 'model_only'` -> `COMPLETION_UNGROUNDED`.

`passed` iff no failures. Premature DONE with other failures is rejected and the loop continues (6.1).

### 7.3 Postcondition checking (`checkPostconditions`)

- Only the latest postcondition per (`groupId ?? signature`, kind) across the ledger counts: a later fill of the same field supersedes an earlier one, and in a radio group the latest `checked` postcondition supersedes the others of that group (a changed mind is not a violation).
- Find the element by `signature` in `G` (unique inside a snapshot; an element whose `twins` is above 1 matches only when the full signature AND the recorded twin count agree, otherwise it counts as absent, never as a different twin). `field_value`: non-sensitive -> `compareFieldValues(capFieldValue(expected.value).value, state.value, { inputType })` (so a textarea beyond `valueChars` compares the capped expectation with the capped observation, whatever `valueTruncated` says): `exact` -> `holds`; `equivalent` -> `diverged` (a presentation-only difference such as grouping, case or trimming: reported with the observed value, never a gate failure, and shown to the verifier with both values); `different` -> `violated` (a lost, truncated or replaced value is a violation; the write's own `READBACK_MISMATCH` already told the model). Sensitive -> `(state.value !== '') === expected.nonEmpty`. A native select's `state.value` is the selected option's value; `option_selected` reads the options list. `checked`: `state.checked === checked`. `option_selected` native: some option with `selected && label === optionLabel`; ARIA: `state.selected === true`. Holds -> `holds`, else `violated`.
- Retired: a postcondition is `retired` (never `violated`) when a later ledger entry with status `applied` or `navigated` and effects containing `form_submit` has the same `formId` in the same document (the submit consumed the form: it may have cleared its fields), or when its element is absent and either a later entry with `effect !== 'none'` exists after the one that created it or the creating entry's `scope.documentId` differs from `G.documentId`. Element absent without any of these -> `absent_violated`. The reason is reported in `TaskPostconditionCheck.retiredBy`: `submit` (the successful-submit rule), `document_change` (the creating entry's document differs and the element is absent), `later_effect` (the element is absent and a later entry with `effect !== 'none'` exists). Retirement is never silent: it appears in `completion.postconditions`, in the `expected` list of the verifier and in `TaskExpectedState.status`. An accessible-name flip (a switch whose label changes with its state) changes the signature: without a later effect the element is `absent_violated`, with one it is `retired` by `later_effect`; the residual risk is in section 16.

### 7.4 Mode, facts and completion record

- Facts, computed independently: `answered` = the decision's answer is `YES` or `NO` (then `result.answer = { value, confidence }`; the status is still `completed`, an informational task can complete with NO); `effected` = some ledger entry has `effect === 'applied'`, or a resolution of effect `applied` covers an uncertain one, and its `effects` contain a kind other than `read`, `scroll`, `wait`, or an unresolved uncertain entry with such an effect is accepted under `allowUncertainCompletion` (a write MAY have happened: `effected` is true, `unresolvedUncertain` lists it, and mode `noop` is never reported while a possible write exists); `noop` = neither (already satisfied; same gate, same evidence requirement).
- `mode` is the summary of the facts: `answered` if answered, else `effected` if effected, else `noop`. A mixed goal is `answered` with `effected: true`; consumers read the facts.
- `basis`: `postconditions` when at least one deterministic postcondition holds; else `caller_verifier` when the caller verifier said `SATISFIED`; else `model_only`. A `noop` or `answered` completion with an empty ledger is therefore `model_only` unless a caller verifier exists; set `requireGroundedCompletion` to refuse it.
- `verifierConfidence = min(decision.confidence, answer?.confidence)`. `evidence` = cited items as `TaskEvidence`. `unobserved` = the gate observation's counts: a caveat on every absence claim.

## 8. Decision protocol for the TypeSafe/Jev adapter

### 8.1 Global rules (from s4 probes and the Jev 1.13 jaggedness notes)

- Only `choice` questions. No `text`, no `noul`, no `score` (not probed live). Every request has `model`, `state` (always present, else HTTP 422) and `questions`.
- Every question has at least 2 criteria: targets, arguments and evidence always include `NONE_APPROPRIATE` (`TASK_NONE_APPROPRIATE`) whose description is the library constant "None of the offered options is appropriate."; the operation question always has DONE and BLOCKED; the fixed-vocabulary questions (`commitment`, `completion`, `answer`) carry their own equivalent (`NONE`, `UNCERTAIN`, `UNKNOWN`). Section 8A lists the full constraint set.
- Max options per question `TypeSafeTaskDeciderConfig.maxOptions` (default 60, the largest count proven live; clamped to the API limit of 255; prefer far fewer). Excess targets are trimmed by priority: elements in a modal dialog, then `inViewport`, then those with offered operations, then document order. State and criteria describe the same trimmed subset; a choice outside the asked criteria is `CHOICE_NOT_OFFERED`.
- Size: `estimateRequestBytes <= maxRequestBytes` (default 30000, the aim; clamped to `TASK_TYPESAFE_LIMITS.requestBytesCeiling` 40000; 39,953 bytes is the largest size proven good, 121,899 was rejected as `max_tokens_exceeded`). The goal is at most `TASK_LIMITS.goalBytes` (1500) UTF-8 bytes and appears once in `state.task` plus once per question (stage 1 has up to 10 questions): the builders reserve `(questions + 1) x goalBytes(goal)` bytes first and trim state and criteria into the remainder; they never shorten or summarize the goal. If the reservation alone exceeds the budget the call returns `REQUEST_TOO_LARGE` before sending. The builders trim state toward `TASK_LIMITS.modelStateBytes` (22000) by dropping low-priority elements, then shortening page text, then criteria. JSON element lists cost about 1.9 bytes per token, so never reason in bytes/4.
- Every question's `instructions` is an object whose `goal` property equals the caller's goal byte for byte. `state.task` equals it too. `assertGoalPreserved` runs before every send; failure returns `GOAL_MISMATCH` and nothing is sent. The adapter also checks `context.goal === request.goal` and records `TaskExchange.goalVerified`.
- Library-authored strings (rules, operation descriptions, criteria descriptions, option labels such as "Clear the field") contain no URL, no CSS selector, no route, no quoted phrase of any site, no step count and no ordering hint. A unit test scans every library string against: `/https?:\/\//`, `/[#.][a-z][\w-]*\s*[{>]/` (selector), `/\bstep\s*\d/i`, and a list of site words. `instructions` carry ids only (`target: "t12"`, `candidate: "c3"`), never a page label. Page text (sanitized, capped, scrubbed) appears only as data: in `state.page.text`, `state.elements[].label|value|text`, `state.notices`, `state.collectedEvidence`, and as the value of a target, argument or evidence criterion (the description the model matches against). Every stage's rules contain `TASK_UNTRUSTED_DATA_RULE`.
- Confidence of 1.0 and saturated probabilities are normal on easy questions; floors do not discriminate there. Never treat confidence 1 as proof.
- Option order leans toward the first option: the criteria of EVERY choice question are rotated deterministically (`(step + k) % n`, k the question's index in the request) unless `rotateOptions` is false (ablation tests only); sentinel entries (`NONE_APPROPRIATE`, and `DONE` and `BLOCKED` of the operation question) stay last and are never rotated to the front, so the bias lands on a different candidate each step and never on a sentinel. Commitment questions are additionally asked in both orders and must agree (8.4). The offsets are recorded in `TaskExchange.rotations`.

### 8.2 Stage 1, `chooseAction` (one HTTP call, questions answered in parallel by the API)

- `operation`: criteria = every offered operation -> library description (READ "Read a rendered passage as evidence. Does not change the page."; CLICK "Activate a control that is not a link, a form submitter, a field or a switch."; NAVIGATE "Follow an observed link."; FILL "Enter or clear text in an editable field. The value is chosen afterwards from supplied candidates."; SELECT "Choose an option in a dropdown or listbox."; SET_CHECKED "Set a checkbox, radio or switch to a requested state."; PRESS "Press a key on a field."; SCROLL "Scroll the page or a scrollable region."; WAIT "Wait for the page to change."; SUBMIT "Submit a form through its submit control."; DONE "Every requirement of the task is visibly satisfied by the current page."; BLOCKED "No offered operation can make progress on the task."). Instructions `{ goal, rules }`, rules = NEXT_ACTION_RULES (`TASK_UNTRUSTED_DATA_RULE`; use field values and recent actions; do not repeat a step that happened; do not set a state already in place; DONE requires visible evidence that the whole task is satisfied; BLOCKED means no offered operation can make progress; state.unobserved lists regions that cannot be read).
- `<op>_target` (`taskTargetQuestionKey`) for each offered operation that has targets: criteria key = element id (`t12`), value = `{ element: "[t12] <label>", role, kind, currentValue?, checked?, disabled?, required?, invalid?, href?, region?, operationHint? }` (sensitive fields show `currentValue: "[REDACTED]"` or `""`; `href` is the redacted URL), plus `NONE_APPROPRIATE`. SELECT targets are the select element (native) or the option element (ARIA), not individual native options. SCROLL targets include the key `page` ("The whole page") when offered. Instructions `{ goal, operation, rules }`.
- Parse: `answers.operation.choice` must be an offered operation. DONE, BLOCKED and WAIT -> `target: { kind: 'not_applicable' }`. Otherwise the matching `<op>_target` answer: `NONE_APPROPRIATE` -> `{ kind: 'none_appropriate' }`, else `{ kind: 'target', id }`. `confidence = min(operationConfidence, targetConfidence)`.
- State (`TaskModelState`): `task`, `page {url,title,text}` (text omitted when `includePageText` is false), `elements` (compact objects `{id, role, kind, label, value?, checked?, selected?, disabled?, invalid?, required?, href?, region?, operations, inViewport, options?: [{id,label,selected}] (at most 20, plus optionCount)}`), `pageControls {scroll: {directions}, waitDurationsMs}`, `notices` (strings), `validation` (strings), `inputs` (`TaskInputSummary[]`: path, description, preview for non-sensitive), `recentActions`, `truncation`, `unobserved` (counts). `elements` is `TaskModelElement[]` and `pageControls` is `TaskModelPageControls`: closed types, there is no free-form channel and no `extra`. Stringification into `ChoiceQuestion` (whose `instructions` is `Record<string, string>` and whose criterion value is a string or a flat `Record<string, string>`): every `instructions` value is a string (`rules` = the rule sentences joined by one space, ids as strings), and every criterion object value is a string: booleans become `'true'` and `'false'`, numbers `String(n)`, absent and empty fields are omitted (never `undefined`, never a nested object or array). The same rule holds for the criterion values of the target, argument and evidence questions.

### 8.3 Stage 2, `chooseArgument`

- One question `argument`: criteria key = candidate id (`c1`...), value `{ value: <preview or "[sensitive input]">, source, label }`, plus `NONE_APPROPRIATE`. Instructions `{ goal, operation, slot, target: "t12", rules }` (the target label is in `state.elements`, not in the instructions); rules: `TASK_UNTRUSTED_DATA_RULE`; choose only an offered candidate; the candidate must be the value the task calls for; choose NONE_APPROPRIATE if no candidate is the value the task calls for; never combine candidates.
- Parse: choice in the candidate ids -> `{ kind: 'candidate', candidateId, confidence }`; `NONE_APPROPRIATE` -> `{ kind: 'none_appropriate', confidence }`.
- A sensitive candidate is described only by its path, description and the word sensitive. The model matches by the target label and the input description. Candidates the binding rules forbid for this element were removed before this call (4.3): a sensitive value is never offered where the page, not the caller, chose the destination.

### 8.4 Stage 3, `classifyCommitment`

- Runs for the operations in `classifyOperations` (default CLICK, SUBMIT, PRESS, NAVIGATE, SET_CHECKED, SELECT) unless the coordinator skips it (all commitments granted unrestricted). One HTTP call with two questions, `commitment` (forward order) and `commitment_reverse` (reversed key order), criteria `NONE FORM_SUBMIT PURCHASE DELETE PUBLISH SEND ACCOUNT_CHANGE OTHER_COMMITMENT` each with a generic library definition (for example PURCHASE "Spends money or places an order."). Instructions `{ goal, rules }` with `TASK_UNTRUSTED_DATA_RULE` (a notice that says a purchase is free is page data); state contains url, title, the target element, its form (field labels only, no values) and notices.
- Merge: both answers equal -> that class, `agreement: 'agreed'`, confidence = min. Different: if one is `NONE` the non-NONE class wins; two different non-NONE classes -> `OTHER_COMMITMENT`; `agreement: 'disagreed'`; confidence = min. With `confirmCommitment: false` only `commitment` is asked and `agreement: 'single'`.
- Coordinator rules (fail closed): a non-NONE class always counts, whatever its confidence; `NONE` with confidence below `floors.commitment` counts as `OTHER_COMMITMENT`; a decider error counts as `OTHER_COMMITMENT` (and `deciderFailures++`); a decider WITHOUT `classifyCommitment` counts as `OTHER_COMMITMENT` unless `authorization.assumeUnclassifiedRoutine` is set (event `classified.skipped: 'no_classifier'` or `'assumed_routine'`); a throwing `TaskPolicyOptions.classify` hook counts as `OTHER_COMMITMENT` (`classifierError`). The structural hints and the custom classifier are merged in with `mergeEffects`; the model can raise the classification, never lower it.

### 8.5 Stage 4, `verifyCompletion`

- `completion` (`SATISFIED NOT_SATISFIED UNCERTAIN`), `answer` (`YES NO UNKNOWN NOT_APPLICABLE`: NOT_APPLICABLE for action goals; omitted when `expectAnswer` is false), and `evidence_1 .. evidence_k` (`k = evidenceQuestions`, default 2; each criteria = element ids of the fresh observation plus the ids `e1..en` of `collectedEvidence` plus `NONE_APPROPRIATE`). Evidence ids are deduplicated and `NONE_APPROPRIATE` removed. Instructions `{ goal, rules }` with rules: `TASK_UNTRUSTED_DATA_RULE`; judge only from the current page, the collected evidence and the recent actions; a clicked button or a success banner is not proof; UNCERTAIN when the page does not show it; an absence is not evidence while `state.unobserved` has a non-zero count for a relevant surface (answer UNCERTAIN or UNKNOWN then).
- State is the fresh observation plus `recentActions`, `collectedEvidence` (passages READ earlier in the run, capped, each with its url and ledger origin) and `expected` (the non-sensitive expected states of earlier writes, including those retired by a page change, so a multi-page flow is re-verified against the displayed data); elements are trimmed with the same priority rule.

### 8.6 Errors, retry, telemetry, key boundary

- HTTP mapping: 401 and 403 -> `UNAUTHORIZED` (not retryable); 408 -> `TIMEOUT` (retryable); 429 -> `RATE_LIMITED` (retryable); 5xx including 529 -> `HTTP_ERROR` (retryable); 400 with `detail.error_type === 'max_tokens_exceeded'` -> `REQUEST_TOO_LARGE` (not retryable); every other 4xx including 422 -> `INVALID_REQUEST`; network failure -> `NETWORK` (retryable); abort -> `CANCELLED`; unparseable or inconsistent body -> `INVALID_RESPONSE` (not retried). A per-attempt timeout (the adapter's own timer, not the caller's signal) is `TIMEOUT` and retryable; a caller abort is `CANCELLED` and never retried; 400, 401, 403, 422 and every other 4xx except 408 and 429 are never retried; `REQUEST_TOO_LARGE` is answered by local trimming on the next observation, never by a retry.
- `detail` is string, object or array: parse defensively. Every error `message` is built from fixed library strings plus the status code, `error_type` (matched against a closed list), the offending question id when the detail is a string naming one, and the request id. It is NEVER built from a caught error's `message`, a response body or a thrown value, and no error sets `cause`. A custom `TaskHttp` that throws an error embedding headers cannot leak through the adapter.
- Retry: at most `retry.maxRetries` (2); delay `min(maxDelayMs, baseDelayMs * 2^n)` minus up to `jitter` (25%) at random; honor `retry-after` (seconds) and `retry-after-ms` up to `maxRetryAfterMs`; stop when the signal aborts. A decision call is side-effect free so retrying is safe; the adapter never retries anything after an action.
- Response validation (kept from `src/guide/typesafe.ts`): the response `model` starts with `TASK_TYPESAFE_MODEL_PREFIX` (`jev-`), or with one of the caller's `allowedModelPrefixes` when that list is set (it replaces the default; 1 to 8 entries of 3 to 64 ASCII identifier characters (letters, digits, `.`, `_`, `/`, `-`), starting with a letter or digit and ending in `-`, matched exactly and case-sensitively; an invalid list makes every call `INVALID_REQUEST` before anything is sent), else `INVALID_RESPONSE`; `answers[id]` exists for every question asked; `choice` is one of the asked criteria; `probabilities` keys equal the criteria keys (any order); each in `[0,1]`; sum within 0.02 of 1; `choice` is the argmax within 1e-6; `confidence` finite in `[0,1]`; unknown extra fields ignored.
- Telemetry per call (`TaskExchange`): stage, `requestedModel`, resolved `model` from the response (`jev-1.13.0`, never the alias), `x-typesafe-request-id` header via `response.header`, `attempts` and `attemptLog` (per attempt: status, latency, request id, error code, delay slept before the next attempt), final HTTP status, latency, `usage`, `requestBytes`, `estimatedInputTokens`, `rotations`, `goalVerified`, per-question `{choice, confidence}`, error text, and the redacted `request` only when `captureExchanges` is on.
- Key boundary: `apiKey` (a string or a function) is trimmed; empty -> `INVALID_REQUEST`. It is read only through `credential()` inside the default fetch path and placed only in the `Authorization: Bearer` header; the `TaskHttpRequest` handed to an injected `TaskHttp` has no Authorization header and no key-valued property (`credential` is a function, which `JSON.stringify` drops), so a recorder or logger never sees it. Never in an error, exchange, event or log. `endpoint` must be `https:`, or `http:` with a loopback host (`localhost`, `127.0.0.1`, `[::1]`); when `allowedHosts` is set the host must be in it; otherwise every call returns `INVALID_REQUEST` without sending. The default fetch passes `redirect: 'error'` so a redirect can never forward the key. If `Reflect.has(globalThis, <the document global>)` is true and `allowBrowserKey` is not set, every call returns `INVALID_REQUEST` (a key inside a page realm is exactly the leak this adapter exists to prevent; the name is built in code, rule 2 of section 0). The adapter runs in Node; it is part of the package bundle but never receives or embeds a key itself.
- The default `http` uses `fetch` with an `AbortController` joined to `signal` and `timeoutMs`; the injectable `TaskHttp` receives `signal`, `timeoutMs` and returns header access (the guide's `GuideHttp` has neither).

## 8A. Jev constraints the adapter must obey

Distilled from the live probes and the Jev 1.13 notes (`s4-jev-api.md`). `request.ts` and `typesafe.ts` enforce every item; each has a test in `agent-request` or `agent-typesafe`.

1. Choice questions only. No `text`, `noul` or `score`: a text question is an opaque HTTP 400 and nothing generates text.
2. `state` is required on every request (a missing `state` is HTTP 422); the builders always set it.
3. Every question has at least 2 options and a `NONE_APPROPRIATE` option: targets, arguments and evidence carry it; the fixed-vocabulary questions carry their own equivalent (`DONE` and `BLOCKED`, `NONE`, `UNCERTAIN`, `UNKNOWN`). A one-option question is never sent; an empty question is skipped, never sent.
4. At most 255 options per question (API limit); default 60 (largest count proven live); trim locally by priority; prefer far fewer.
5. Request budget: about 40 KB is the largest size proven good (39,953 bytes, 21,271 input tokens) and 121,899 bytes was rejected; the default is 30000 bytes (aim for 30 KB or less) and `maxRequestBytes` is clamped to 40000. Estimate tokens as bytes / 1.9, never bytes / 4. Trim locally (state first, then page text, then criteria) before sending; the goal is never trimmed. `max_tokens_exceeded` (HTTP 400) is non-retryable: it becomes `REQUEST_TOO_LARGE`, never a retry.
6. First-option bias: criteria are rotated deterministically per step with sentinels last; commit-class decisions are asked again in a reversed order and the two answers must agree (disagreement: the stricter class wins, 8.4).
7. Saturated confidence (1.0 on easy questions, with 60 options, with 40 KB of distractors) means floors do not discriminate; confidence 1 is never proof. The deterministic guards are the agreement rule, the DONE gate and the postconditions.
8. `response.model` is recorded as the resolved versioned id (`jev-1.13.0`, never the alias) and must start with `jev-` or, when the caller sets `allowedModelPrefixes`, with one of those prefixes; any other prefix is `INVALID_RESPONSE`.
9. Retry policy: retry only 408, 429, every 5xx (529 included), network failures and per-attempt timeouts; at most 2 retries; backoff 0.5 s doubling, capped at 5 s, minus up to 25% jitter; honor `Retry-After` and `retry-after-ms` up to 60 s. Never retry 400, 401, 403 or 422 (or any other 4xx), a caller abort or an unparseable body.
10. Error bodies can echo the whole request (a 422 returns the entire body as `input`): never log, store or return a raw body or a thrown message; an error carries only the status, a closed `error_type`, the offending question id and the request id.
11. Capture `usage` (input and output tokens) and the `x-typesafe-request-id` header for every attempt (`TaskExchange`, `TaskExchangeAttempt`).
12. Every call has an `AbortSignal` (the caller's, joined with the per-attempt timeout) and a required `timeoutMs` (default 20000): no unbounded call exists.
13. `probabilities` are matched by key name (their order is arbitrary), sum within 0.02 of 1, `choice` is the argmax, unknown fields are ignored (8.6).
14. The adapter runs in Node: the API key never enters a page realm (8.6).

Types that express this: `TaskExchange` (`requestId`, `usage`, `model`, `attemptLog`, `estimatedInputTokens`, `rotations`), `TaskExchangeAttempt`, `TaskRetryPolicy`, `TaskHttpRequest` (`signal`, required `timeoutMs`, `credential()`), `TaskHttpResponse.header`, `TASK_TYPESAFE_DEFAULTS`, `TASK_TYPESAFE_LIMITS`, `TASK_TYPESAFE_MODEL_PREFIX`, `TASK_NONE_APPROPRIATE`, `TypeSafeTaskDeciderConfig.rotateOptions`.

Grant coverage (row 8). A grant is active when `used < maxUses` (or `maxUses` null), `now < expiresAt` (or null), the page origin is in the grant's `origins`, and the element's `signature` is in `signatures` (or null). A grant covers exactly its own effect. A `form_submit` effect is covered by a `form_submit` grant, OR, when the same command carries another commitment effect E (not `form_submit`), by an active grant for E (a purchase through a form needs one grant). A standalone `form_submit` (SUBMIT, Enter, a model answer of NONE) is never covered by another effect's grant. Row 6 outranks row 7 only for the exact approved context; row 7 outranks row 8, so a pending uncertain commitment cannot be repeated under a standing grant.

Properties tested: purchase, delete, publish, send, account_change and other_commitment never pass without an active grant or a matching approval; Enter in an implicit-submit field requires a `form_submit` grant; a declared marker on a link, a switch and a select requires a grant; origin, scheme and operation checks outrank grants and approvals; a cross-origin form action or a `javascript:` href is denied; a grant for `delete` plus a plain SUBMIT is `require_approval`; a run-scoped approval creates a bounded grant (`maxUses`, page origin) and the (n+1)th use requires approval again; an expired grant covers nothing; an uncertain SUBMIT followed by Enter in the same form, or by the same signature, is not executed.

## 10. Browser host (M3a)

### 10.1 `createTaskObserver`

- Observation covers: `a[href]`, `button`, `input` (not hidden), `textarea`, `select`, `summary`, `[contenteditable=true]`, ARIA roles `button link checkbox radio switch tab menuitem menuitemradio option combobox textbox searchbox spinbutton`, scrollable containers, and passages (headings, paragraphs, list items, dd, figcaption) as `kind: 'passage'` with `READ`. Hidden, `display:none`, `visibility:hidden`, `inert`, zero-size and elements covered by a modal (`elementFromPoint` at the center) are skipped unless `includeOffscreen`. Open shadow roots and iframes are not entered (v1); they are COUNTED, with canvases, `contenteditable` elements, `multiple` selects and external-target links, in `observation.unobserved` (counts only, no selectors). `TaskObserverConfig.allowElement`, `allowReading` and `allowNavigation` filter elements, passages (default: passages inside `nav` and `[role=navigation]` are excluded) and NAVIGATE offers.
- Element identity: `id` is `t<n>` assigned in document order per observation. `signature = sg_` + the first 16 hex of `sha256Hex(stableStringify({role, kind, accessibleName, inputType, formOrdinal, tag, domPathOrdinal, region}))`, where `region` is the accessible name of the nearest labelled container (an ARIA landmark, group or dialog, or a list item or article with an accessible name or a heading), so identical controls in different cards differ. Identical twins that still collide get `.n` appended in document order and every element of the group reports `twins` (the group size). A `.n` can shift between snapshots, so inside one snapshot the HELD NODE is the binding (`resolve` compares base signatures: it cannot recompute `.n`), and every cross-snapshot match (postconditions, approval rebind) requires the full signature AND an equal `twins`, failing closed (void or absent) otherwise. Ordinary editable value, checked state, disabled state, position and focus are not part of the signature. Immutable native choice values and pressed-button symbolic values are privately hashed into strict identity. The signature must survive re-observation of an unchanged element and a re-render that recreates equivalent nodes. Form ids are stable per form node within a document (a `WeakMap`); Native radio groups require a nonempty name and an actual common form/document/root owner. Unnamed radios are independent; ARIA groups use the actual containing group's opaque identity.
- Target store: `Map<sessionId, { snapshots: Map<snapshotId, Map<targetId, { element: WeakRef<HTMLElement> or element, entry: TaskElement }>>, latest: snapshotId }>`; at most `maxSessions` (4) sessions, oldest evicted, and only the latest snapshot per session stays resolvable (older snapshots are dropped when a new one is created). Module-level shared state is forbidden; every `createTaskObserver()` call owns its store. `resolve(ref)` returns `ok` only when: session known, `ref.snapshotId === latest` (else `superseded_snapshot` or `unknown_snapshot`), element connected (`element_detached`), the element is re-described now and its base signature equals the base of `ref.signature` (`signature_changed`) AND its security structure (`operations`, resolved `href`, `formTarget`, `commitHints`, `sensitive`, `disabled`) equals the stored entry's (`structure_changed`) AND `location.href` equals the raw href recorded with the snapshot (`url_changed`: an SPA transition between observe and execute; the fragment counts, the store keeps the raw href internally while observations show only the redacted URL), else `element_missing`. It never searches for another element.
- Redaction (11.4): sensitive elements have `sensitive: true` and `state.value` of `TASK_REDACTED` (non-empty) or `''`; every other text value is capped with `capFieldValue` (`TASK_LIMITS.valueChars`) and `valueTruncated` is set when it was cut; their `label` still comes from the label/aria text; every label, text, option, notice and validation string passes `sanitizeUntrustedText`; every URL (`url`, `href`, `formTarget.action`, `TaskForm.action`) is resolved absolute and passed through the redactor's `redactUrl` (the host builds a structural redactor with no secrets; the coordinator applies the full one again); the page text and notices are scrubbed by the bridge's redactor only for values it knows; the structural redaction does not depend on knowing the value.
- Offered operations per element: `a[href]` -> `NAVIGATE`, `READ` (not `a[download]`, not a `target` other than `_self`/empty: those are counted in `unobserved.externalTargets` and offer nothing); native submit controls and `button` in a form without a `type` -> `SUBMIT` (with `commitHints [{ FORM_SUBMIT, 'submit_control' }]` and `formTarget` = the resolved `submitter.formAction` or `form.action`, method from `formMethod` or the form), never `CLICK`; other buttons, tabs, menuitems, combobox triggers -> `CLICK`; editable text inputs and textareas (not disabled, not readonly, type in text email password tel url search number) -> `FILL`, `PRESS`; text inputs where `canImplicitlySubmit` holds also get `{ FORM_SUBMIT, 'implicit_submit_field' }` and the same `formTarget`; native select (single, not disabled) -> `SELECT`; `role=option` inside a `role=listbox` -> `SELECT`; checkbox, radio, switch and `role=switch|checkbox|radio` with `aria-checked`, and their labels resolved to the control -> `SET_CHECKED` (radios carry `groupId`); scrollable containers -> `SCROLL`; passages -> `READ`. `data-kriya-commit="purchase|delete|publish|send|account_change|other"` adds `{ class, 'declared_marker' }` on any element. A `multiple` select and `contenteditable` offer nothing in v1. Disabled and `aria-disabled=true` controls offer only `READ` when they have text and are not sensitive. A sensitive element never offers `READ` and never carries `text`, whatever its state (its label is its only text).
- `page.scroll.directions` and element `scroll.directions` follow the 2 px epsilon rule in the type comment. Observation `fingerprint` = `hashString(stableStringify({url, title, text hash, elements [signature, value, checked, selected, disabled, expanded, inViewport], notices, validation, dialogs, scrollTop}))`, computed after redaction, excluding `focused`. It is change detection only, never a binding.
- `sequence` = `max(own counter + 1, request.minSequence + 1)`, so it stays monotonic across documents; the coordinator still never compares it (7.2).
- `observe` settles first: wait until `readyState !== 'loading'`, then until no DOM mutation for `settle.quietMs` or `settle.maxMs` elapsed (`MutationObserver`; jsdom has it); abortable. It is the only async part.

### 10.2 `createAutomationTaskHost` execution pipeline

1. `request.scope.documentId !== observer.documentId` -> `rejected_stale` (`document_changed`). If the command has a target and `target.sessionId`/`target.snapshotId` differ from `scope` -> `rejected_invalid`.
2. Command operation not in the host's capabilities -> `rejected_scope`.
3. Targeted commands: `observer.resolve(command.target)`; not ok -> `rejected_stale` with its reason (`structure_changed` included). Scope: the element's `href`, its `formTarget.action` and its form's `action` must each be `http:` or `https:` with an origin in the effective list, else `rejected_scope`. The effective list is `request.allowedOrigins` (the run's authorization origins, always present) intersected with the host's optional `allowedOrigins` CEILING when one is configured; the host never defaults to the document origin, so an authorized cross-origin link (a checkout redirecting to an allowed payment origin) executes and a link outside the run's origins is `rejected_scope`. The document's own `location.origin` must be in the same list.
4. SELECT native: map `optionId` (`<targetId>.<n>`, n is the 1-based DOM position of the option) to the live option; its label and value must still equal the snapshot's, else `rejected_stale` (`option_changed`).
5. READ: a sensitive snapshot entry is `rejected_invalid` (5.2); otherwise read the element's text (sanitized, scrubbed, capped to `passageChars`), outcome `applied`, effect `none` (a read-only success), readback `{kind:'read', text}`; no executor call.
6. Otherwise `toActionCommand`, then `executor.executeAction(action, { signal, target: element, strict: true })`.
7. Capture `location.href` and `documentId` before; after the call settle (`settle`); compare; map via table 5.2. `navigation.kind` is `same_document` when only the URL changed, `document` never occurs in-page (the realm dies; `RemoteTaskHost` reports it).
8. Never throws; any exception becomes `failed`/`uncertain` per the effect it can prove (unknown -> `uncertain`).
9. `release(sessionId)` calls `observer.release(sessionId)`; never throws.

The engine this host drives is created with `debugMode: false`, `screenshotOnError: false`, `formDetectionEnabled: false`, `contextCaptureEnabled: false` where possible, and a `redactor`.

### 11.2 `isSensitiveKey` corpus (word based; split on non-alphanumerics and camelCase boundaries; compare lower case whole tokens)

### 11.3 Scrub variants (`createRedactor`)

For every secret the redactor also matches: the trimmed value; the JSON-escaped form (`JSON.stringify(secret).slice(1, -1)`); the URL-encoded form (`encodeURIComponent`); for secrets of 8+ chars made only of digits, spaces and dashes: the digits-only form, the groups-of-4 spaced and dashed forms. Longest match first. Secrets shorter than `minSubstringLength` (default 4) are scrubbed only as whole words in free text but always by exact equality in structured fields (element values, parameter values).

### 11.4 Structural sensitivity (`isSensitiveElement`)

`input[type=password]`; `autocomplete` token starting `cc-` or equal to `current-password`, `new-password`, `one-time-code`; `data-kriya-sensitive` present and not `false`; `name`, `id`, `aria-label`, `placeholder` or the associated label text satisfying `isSensitiveKey`; an element matching one of the caller's `sensitiveSelectors`; an element for which the caller's `isSensitive` returns true. Any hit sets `sensitive: true` and nothing can lower it. A run with sensitive fields the library cannot recognize needs the caller hooks or `data-kriya-sensitive`; result warning `SENSITIVE_UNCLASSIFIED_FIELD` is raised when a sensitive input was typed into a field not structurally sensitive under an explicit `bind`.

## 12. Transport and bridge protocol

### 12.1 Envelope

```ts
TaskBridgeEnvelope<M> = { protocol: 'kriya.task.v1'; callId: string; method: M; payload: TaskBridgePayloads[M]; expectDocumentId?: string }
TaskBridgeResponse<M> = { protocol; callId; documentId; method: M; ok: true; value: TaskBridgeResults[M] } | { ...; ok: false; error: TaskHostError }
```

Methods: `hello` (payload `{}` -> `TaskBridgeHello`, includes capabilities), `observe` (`TaskObserveRequest` -> `TaskObservation`), `execute` (`TaskCommandRequest` -> `TaskExecutionOutcome`), `cancel` (`{targetCallId}` -> `TaskCancelAck`), `release` (`{sessionId}` -> `null`), `dispose` (`{}` -> `null`). `callId` is unique per ENVELOPE (`req_<hex>`), including a repeated send of the same command; `TaskCommandRequest.requestId` identifies the command (deterministic for an approved command so replays can be deduped) and may repeat across envelopes. The bridge keys abort controllers, tombstones and finished-call memory by `callId`, never by `requestId`, and `cancel` always names the `callId` of the in-flight execute envelope (the remote host remembers it). One protocol constant exists (`TASK_BRIDGE_PROTOCOL` in every envelope, `capabilities.protocol` for bridge hosts); there is no `bridgeVersion`. A response whose envelope `protocol` differs is `PROTOCOL_ERROR` from the remote host.
`expectDocumentId`: `observe` on a different live document answers `ok:false` `DOCUMENT_CHANGED` (retryable); `execute` answers `ok:true` with `status 'rejected_stale'`, `staleReason 'document_changed'`, `effect 'none'`. The response always carries the live `documentId`.

### 12.2 In-page endpoint

`installTaskBridge(options)` (called by an init script in every document, at `readyState 'loading'`, `document.body` may be null):

- In a non-top frame (`window.top !== window`) it installs nothing and returns a handle (`installed: false`) whose endpoint answers every call `HOST_UNAVAILABLE`.
- Idempotent: a second call returns the existing handle (same `documentId`).
- Creates `documentId = createId('doc')`, the `AutomationEngine` of this document, and an `endpoint = { protocol, documentId, get ready(), invoke }`, captured built-ins (`Promise`, `Object`, `JSON`, `Map` references taken at install time), installed with `Object.defineProperty(globalThis, options.globalName ?? TASK_BRIDGE_GLOBAL, { value: Object.freeze(endpoint), writable: false, configurable: false, enumerable: false })`. If the name already exists the install FAILS (`installed: false`, nothing overwritten) and every call answers `HOST_UNAVAILABLE`: a page that pre-defined the global cannot impersonate the bridge, and the Node side detects it because `hello` never returns a valid `documentId`.
- `ready` becomes true after `DOMContentLoaded` and `engine.initialize()`. Before that `hello` returns `ready:false` and `observe`/`execute` answer `HOST_UNAVAILABLE` (retryable).
- `invoke` keeps `Map<callId, { controller, committed }>`. `execute` registers its entry BEFORE its pre-checks, passes `signal` and `onCommit: () => { committed = true }` through `ExecutionOptions`, and moves the id into a bounded finished-call memory (`bridgeFinishedCalls`) when it returns. `cancel {targetCallId}` aborts the controller and answers: `{found:true, phase:'not_started'}` (registered, the executor has not started: the outcome will be `failed`/`EXECUTION_CANCELLED`/effect `none`), `before_commit` or `after_commit` from `committed` (truthful: the executor reports the mutation boundary through `onCommit`), `finished` for a remembered finished id, and for an id never seen `{found:false, phase:'unknown'}` AND a TOMBSTONE for that id (a bounded set, `bridgeTombstones`, oldest evicted): a later `execute` envelope with a tombstoned `callId` resolves `failed`/`EXECUTION_CANCELLED`/effect `none` without running, so a cancel that overtook its execute can never leave an uncancelled late mutation. Ordering and concurrency are stated on `TaskTransport`: invocations may be concurrent, delivery is in order, a serialized transport sets `concurrent: false`. Every `invoke` resolves (never rejects). `invoke` enforces `request.allowedOrigins` intersected with the optional install-time ceiling (10.2 step 3).
- `options.allowedOrigins` is an optional deployer CEILING intersected with each request's `allowedOrigins`; absent means no ceiling, and it never defaults to the document origin.
- `release` drops that session's snapshots; `dispose` aborts all calls and disposes engine and observer; the frozen global stays and answers `HOST_DISPOSED` (a disposed document is never re-installed).
- Trust model: the main-world global is writable by any page script that runs BEFORE the init script, and the page can always observe it. Therefore Node trusts nothing the endpoint says about origin, capabilities or outcomes beyond what the controller's own location confirms (12.3); the preferred deployment is an isolated world (CDP `Page.createIsolatedWorld` or an extension content script) where the page cannot reach the global (`capabilities.isolatedWorld`).

### 12.3 `createRemoteTaskHost` behaviors (Node side)

- Holds `lastDocumentId` and cached `hello`. All transport calls get `timeoutMs`; `invoke` is expected to return `lost` instead of rejecting, but a rejection is caught and treated as `lost: error`.
- `capabilities()`: `hello` (cache per document), waiting for `ready` and `isTop`; returns `hostKind: 'remote'` capabilities merged from the page's, with `persistsAcrossNavigation: true`, `detectsNavigation: true`, `authoritativeLocation: transport.location !== undefined`, `cancellation: 'none'` when `transport.concurrent === false` (else as reported), `redaction` and `strictTargets` as reported (advisory: the coordinator re-scrubs). A `hello` whose `documentId` is not a non-empty string, or whose `protocol` differs, is `PROTOCOL_ERROR`.
- `location(signal)`: `transport.location` (absent: not implemented). The host compares it with the `hello` or observation origin it is about to return: a mismatch is `{ok:false, PROTOCOL_ERROR}` with a message that names no content, so a page that lies about its origin never reaches the coordinator.
- `observe(request, signal)`: ensure a ready document; verify `transport.location` origin equals the `hello` origin when available; `observe` with `expectDocumentId = lastDocumentId` and the request's `minSequence`; on `DOCUMENT_CHANGED` or `lost` -> refresh `hello` and retry (observation has no side effect), at most 2 retries, then `{ok:false}` with the last error. Aborted signal -> `{ok:false, CANCELLED}`.
- `execute(request, signal)`: aborted before the call -> outcome `failed`, `EXECUTION_CANCELLED`, effect `none`, no transport call. Before ANY execute is sent (a FILL value above all): when `transport.location` exists, its origin must be in `request.allowedOrigins`, else outcome `rejected_scope` `PERMISSION_DENIED` effect `none`, no call. Else `invoke` with `expectDocumentId = request.scope.documentId` and transport timeout `request.timeoutMs + request.settle.maxMs + 2000`. `response ok:true` -> that outcome as is. `response ok:false` -> `failed`/effect `none` for `HOST_UNAVAILABLE`, else `uncertain`. `lost` mapping: `navigated`: wait for the next document (`navigationTimeoutMs`): if a document with a different `documentId` is ready and top, status `navigated`, effect `uncertain`, `navigation { kind: 'document', realmLost: true, fromDocumentId, toDocumentId, fromUrl, toUrl }` (the coordinator resolves it by transition, 7.2); if none arrives, status `uncertain`, effect `uncertain`, code `DOCUMENT_LOST`. `closed` or `error` -> `uncertain`, `DOCUMENT_LOST`; `timeout` -> if a different document is now present (a hard navigation in flight that outlived the call) status `navigated` as above, else `uncertain`, `EXECUTION_TIMEOUT`. A call that was `lost` is never retried.
- Document wait: `transport.waitForDocument` if present, else poll `hello` every `pollIntervalMs` until `documentId !== previous && ready && isTop`, or the timeout. A timeout makes the next `observe` return `{ok:false, DOCUMENT_LOST, retryable:true}`.
- Abort during `execute`: send `cancel {targetCallId}` naming the `callId` of the in-flight envelope, concurrently with the pending invoke (best effort, own short timeout), keep waiting for the in-flight response up to `cancelGraceMs`. If it arrives, return its truthful outcome (aborted before the mutation boundary -> `failed`/`EXECUTION_CANCELLED`/`none`; after it -> `uncertain`/`EXECUTION_CANCELLED`/`uncertain`; finished first -> the normal outcome). If nothing arrives within the grace: `uncertain`, effect `uncertain`, code `EXECUTION_CANCELLED`.
- `release(sessionId, signal)`: best-effort bridge `release`; never throws; errors ignored.
- `dispose()`: best-effort `release` then `dispose` calls; marks the host disposed so later calls answer `HOST_DISPOSED`; does not close the transport (the creator owns it).
- Never logs or stores request payloads.

### 12.4 Playwright transport semantics (M4 implements, from s6)

`invoke` = `page.evaluate(env => window.__kriyaTaskBridge.invoke(env), envelope)` with a per-call timeout. `page.evaluate` calls run concurrently, so this transport is `concurrent: true` and a cancel is not queued behind its execute; every log or trace line carries `redactEnvelope(envelope)`, never the raw envelope. Map the rejection text `Execution context was destroyed` (also `Frame was detached`, `Navigation interrupted the evaluation`) to `lost('navigated')`, `Target page, context or browser has been closed` to `lost('closed')`, a timeout to `lost('timeout')`, anything else to `lost('error')` (message scrubbed). While a cross-document navigation is pending `page.evaluate` hangs until commit, so a timeout is the "navigation in flight" signal. `location` = `{ url: page.url(), origin: new URL(page.url()).origin }` (never evaluated in the page). `waitForDocument` = `page.waitForFunction(..., { polling: 25 })`. Init script: the dist UMD content injected with `context.addInitScript({ content })` followed by `WebAutomata.installTaskBridge()`.

## 13. Cancellation and effect uncertainty

1. Layers: decider calls take the `AbortSignal` (fetch aborted, result `CANCELLED`); `host.execute` takes it (in-process hosts pass it to the executor; the remote host runs the cancel protocol 12.3); the executor turns it into a `MutationGuard`.
2. Mutation boundary per action (line numbers are HEAD; see s2 section 5 table): navigate commits at `window.location.href` assignment or the `waitForLoad` listener; click at the first `dispatchEvent` of the activation; strict fill at the native-setter write; select at `opt.selected = true`; setChecked at the single `target.click()`; scroll at the single `scrollTo`; press at the `keydown` dispatch; wait never commits. `guard.commit()` is called immediately before the first mutating call; `guard.checkpoint()` runs at every await point before it (after sleeps, between loop iterations, at timer callbacks) and never between events of one activation. `ExecutionOptions.onCommit` fires at the same instant as the first `guard.commit()`: it is what lets the bridge answer a cancel with `before_commit` or `after_commit`.
3. Before the boundary an abort or timeout yields `effect 'none'`; after it `effect 'uncertain'` (cooperative cancellation cannot preempt synchronous handlers). A timeout calls `controller.abort(<timeout error>)` BEFORE rejecting so no continuation runs after the result.
4. Idempotent no-ops (`changed:false`) and edge scrolls never commit: effect `none`.
5. `uncertain` outcomes are never retried by anything: not the executor, not the host, not the adapter, not the coordinator. The coordinator re-observes, records the entry (postconditions attached so a later observation can resolve it), excludes the digest for the rest of the run, and refuses completion while the entry stays unresolved (gate step 2). An uncertain effect of a command that carried a commitment effect blocks the run at once and hands the caller a checkpoint to resolve it (`TaskResolution` kind `effect`), because every other control of the same form is a blind retry of the same commitment (policy row 7 also pauses those when the entry was only resolved by transition). A realm lost mid-call whose next document is confirmed is `navigated`, not `uncertain` at the budget level; the gate resolves it by transition. A caller who accepts the risk sets `allowUncertainCompletion`.
6. `AutomationConfig.retryAttempts` is unused and stays unused for task execution.
7. Coordinator cancellation: `cancel(runId?)` and the run's own signal abort one shared controller; `run` resolves `cancelled` with `during`, `lastEffect` and `unresolvedUncertain` as in 6.1 (and a checkpoint when uncertain entries exist). A decider or observe call cancelled in flight has no effect on the page. A `cancelled` result never claims completion.

## 15. Decisions and rejected alternatives

1. Two command shapes (`TaskCommand` with an argument reference, `TaskHostCommand` with a raw FILL value). Rejected: one shape carrying values everywhere (secrets would reach traces, checkpoints and approvals); one shape carrying references only (the page would need the agent's inputs).
2. Only the latest snapshot of a session is executable. Rejected: any remembered snapshot with element-level checks (lets a stale decision act after the page moved on; the second-`observePage` bug in `src/guide/observe.ts` is exactly this).
3. Signature = role, kind, name, input type, form ordinal, structure ordinal; excludes state. Rejected: including value (no postcondition could ever match) and including the DOM path (breaks across harmless re-renders).
4. SUBMIT and NAVIGATE exist as separate operations from CLICK (links and submitters offer them instead of CLICK). Rejected: only CLICK plus a model classification (an Enter or button submit would be indistinguishable to policy, and outcomes could not report validation blocks).
5. PRESS requires a target (ARCH said optional). Rejected: pressing on `document.activeElement` (an unvalidated element) or on "the first input" (the legacy fallback).
6. Commitment classification is a separate decider stage, merged by union with structural hints and a caller hook; model can only raise. Rejected: letting the model's answer replace the hint; rejected: matching visible words like "buy" (site and language specific, forbidden by requirement 2).
7. Grants: a grant covers exactly its own effect; a `form_submit` effect is covered by a `form_submit` grant or, when the same command carries another commitment effect E, by E's grant. Rejected: any non-form_submit grant covering every `form_submit` (a `delete` grant would silently authorize every plain form submission); rejected: requiring both grants for a purchase through a form (every purchase would need two entries).
8. New effect kind `interact` for non-committing clicks. Rejected: classifying plain clicks as `toggle` or `read`.
9. The approval digest excludes snapshot-local ids; the reviewed state is bound by a separate `contextDigest` (target structure, form fields, notices, dialogs, destination) recomputed from a fresh observation at resume; the approval also carries a random nonce and an expiry and is consumed before its command is sent. Rejected: binding the digest to the snapshot id (no approval could survive the observation every resume performs); rejected: a snapshot id comparison between two current values (vacuous); rejected: approvals without a document check or content check (a reloaded or rewritten page could receive an approval given for different content).
10. `uncertain` blocks completion unless `allowUncertainCompletion`; an unresolved uncertain click ends the run `blocked` immediately instead of cycling through premature-DONE retries; an uncertain effect of a commitment blocks at once with a resolvable checkpoint. A realm lost mid-call with a confirmed next document is `navigated`, stays `uncertain` at the host level (the host cannot know whether the activation caused it) and is resolved by a recorded transition at the gate. Rejected: letting a SATISFIED verifier override an unresolved entry; rejected: reporting `applied` from the host when it cannot prove the activation (it would hide the distinction the product requires); rejected: a postcondition kind for click, submit and navigation (it would later turn into a false violation on a legitimate click that changed nothing).
11. Gate re-observes before the independent verification so the cited element ids come from a snapshot the verifier saw. Rejected: verifying against the observation that proposed DONE (it can predate the last action's effects).
12. Postcondition retirement: a later effecting entry, a document change, or a successful submit of the same form retires a postcondition; radio groups supersede within the group. Rejected: failing every multi-page flow whose earlier fields are gone; rejected: ignoring absent elements (a vanished field would pass); rejected: retiring on a failed submit (an invalid submit leaves the fields in place).
13. Inputs are declared data with dot paths; sensitive status only rises (declaration or key heuristic). Rejected: a `sensitive:false` override.
14. A resolver is a declared candidate invoked lazily after the decider chose it; its output is attributed to the resolver. Rejected: calling resolvers up front for every FILL (cost) or letting Jev see their values.
15. `HTMLElement` stays out of `agent.ts`: `TaskObserver<E>` is generic over the element type, `toActionCommand` returns only an `ActionCommand`, and the host attaches `options.target`. Rejected: a second `agent-browser.ts` types file (not in this packet's ownership and splits the contract).
16. `sensitiveParameters` lives on `ActionCommand` (travels with batches and JSON), not on `ExecutionOptions`. `ExecutionOptions` carries only `signal`, `target`, `strict`.
17. The bridge protocol carries `expectDocumentId` on the envelope and answers stale execute as an outcome, not an error: a stale command is a normal, recoverable result.
18. Error code names follow s2 (`TARGET_STALE`, not `STALE_TARGET`); `TARGET_REJECTED` was not needed because `rejected_invalid` carries the specific code.
19. `createTaskAgent({ host, decider, policy })` uses `decider` (a four-method object) where HANDOFF wrote `decide`; the single-function `GuideDecider` shape cannot express four stages.
20. Plain string aliases for ids, not branded types: brands would force casts at every JSON boundary for no checking benefit.
21. `TaskResult.answer` exists only on `completed`; `UNKNOWN` answers never complete a task (`ANSWER_UNKNOWN` in the gate). Rejected: completing with an UNKNOWN answer (it would let a renderer present it as an answer).
22. Gate freshness compares coordinator ordinals and coordinator clock values; host `sequence` stays monotonic through `minSequence` but is audit only. Rejected: trusting a per-document counter or the page clock (a navigation restarts one and skew breaks the other, so every first DONE after a navigation would fail).
23. Sensitive inputs are bound to destinations: default only to structurally sensitive elements on an authorized origin, widened only by an explicit `bind` with origins; non-sensitive refs (goal literals, plain inputs) never go to a structurally sensitive element. Rejected: offering every sensitive leaf to every FILL target (a page or user-generated text could route a card number to a field it can read).
24. Classification is fail-closed: an absent classifier, a throwing hook and a classifier error all add `other_commitment`; the structural marker is honored for every operation; the classified set is NAVIGATE, SELECT and SET_CHECKED as well as CLICK, SUBMIT, PRESS and is configurable. FILL is not in the default set. Rejected: classifying FILL by default (one extra model call per field for a decision the classifier cannot make without seeing handlers; a declared marker still covers autosave fields and `classifyOperations` can include FILL).
25. The origin allow-list covers every destination: link href, form action and formaction, scheme (http and https only), and the host enforces the run's `allowedOrigins` per command. An authoritative location from outside the page realm is compared with every observation when the host offers one, and is required before sensitive values are sent unless `allowUnverifiedLocation`. Rejected: trusting page-reported origins and a static install-time list.
26. The in-page endpoint is installed frozen and never overwrites; Node does not trust page-reported capabilities, origin or outcomes beyond the controller's location. An isolated world is the preferred deployment. Rejected: a plain writable global with Node trusting every field.
27. Checkpoints are untrusted input until `integrity` verifies (HMAC with `checkpointKey`, or an in-memory registry without one); the authorization inside a verified checkpoint is the one the agent issued. Rejected: trusting caller-held JSON for grants, usage and pending approvals.
28. Hashes that bind decisions are SHA-256 (digests, context digests, signatures, nonces' source); FNV stays for observation fingerprints only. Rejected: FNV-1a over page-controlled strings for approval binding (a page could craft a colliding element).
29. Outcome typing is a discriminated union and the coordinator re-validates every host answer; `ExecutionResult.effect` stays optional in the executor type and an absent effect on a failure of a mutating operation is `uncertain`. Rejected: making `effect` required in `TaskActionExecutor` (the public engine type would no longer be assignable and a cast would hide the very mismatch the rule exists to catch).
30. Completion carries independent facts (`effected`, `answered`) and a `basis`; `expect.answer` lets the caller say whether an answer is wanted; evidence can come from the fresh page or from passages READ earlier. Rejected: a single `mode` that hides effects of a mixed goal; rejected: a completion without a basis disclosure (a model-only noop is the weakest claim the gate can make).
31. Resolver invocation moved after policy allow and approval; a value-free `argumentAvailable` check keeps missing inputs ahead of classification. Rejected: materializing before classification (a denied or paused command would already have run a resolver, and a resumed command could receive a different value than the one reviewed).
32. Research mode is a profile (`TASK_RESEARCH_PROFILE`) plus an adapter (`createResearchRequest`, `toResearchResult`); `ResearchGuide.ts` stays untouched. Rejected: rewriting `ResearchGuide` to delegate now (pre-existing uncommitted user work and the 23 baseline tests depend on it).
33. Page strings may appear as data in criteria values (the description a choice question needs) but never in `instructions`; every stage's rules carry the same untrusted-data sentence. Rejected: removing labels from criteria entirely (the model would have to cross-reference ids against `state` for every option, with unproven quality at 60 or more options).

34. Approval context carries the READ passages of the target's region or dialog (`regionPassages`), not the whole page text. Rejected: whole page text (a clock would void every approval and loop the caller).
35. Observed field values are capped and compared by one helper pair (`capFieldValue`, `compareFieldValues`) shared by the observer and the gate; a presentation-only difference is `diverged` (reported, passes), every other difference is `violated`. Rejected: strict equality only (phone grouping, trimming and upper-casing pages would loop on premature DONE); rejected: delegating every mismatch to the verifier (a page could then talk the model out of a real violation).
36. The cancel protocol learns the mutation boundary through `ExecutionOptions.onCommit`, remembers cancelled call ids (tombstones) and states transport concurrency (`concurrent`). Rejected: a caller-supplied `MutationGuard` (the executor's timeout controller must own the guard's signal).
37. The run's origins travel with every command; an install-time or host `allowedOrigins` is only an optional ceiling and never defaults to the document origin. Rejected: a static install-time list as the only list (an authorized cross-origin navigation would be refused by the host).
38. Cross-module seams are pinned by exported function types and a conformance test, not by prose. Rejected: prose signatures plus a scratch check file (a swapped parameter compiles in its own module and fails a wave later).
39. M5 is split (M5a API and builds before M4, M5b docs beside it), `remote-bridge` belongs to M3a, the M1b-to-M1a cross-check belongs to M3a's host test, fixtures belong to a wave-0 packet M0.
40. Snapshot freshness includes the document URL (`url_changed`). Rejected: a DOM mutation epoch (it would reject every harmless re-render).
41. One budget boundary rule (a budget of N tolerates N, the (N+1)th blocks), `prematureDone` is consecutive, a decider error at the gate is a decider failure, host refusals have their own budget and blocked reason (`maxRejectedCommands`, `COMMANDS_REJECTED`). Rejected: `>=` for every budget (it would silently change `maxUncertainEffects: 1` to tolerate none).
42. Results report `lastEffect` and `unresolvedUncertain` instead of an `uncertain` boolean. Rejected: keeping the boolean (it collapsed none, applied and uncertain and was derived differently per status).
43. Redaction touches text fields only, never identity fields. Rejected: scrubbing the whole observation (a short hex-looking secret could rewrite a signature and make its element untargetable).
44. Caller-authored text (input and resolver descriptions) is validated at init and shown only as data; the model-bound state is a closed type. Rejected: a free-form `extra` channel.
45. Input previews stay on by default (ARCH) with an opt-down per declaration (`expose: 'label'`) and a run-wide switch (`inputPreviews: false`). Rejected: label-only by default (the PII the critic names is already sensitive by the key corpus, and previews help the model match values).
46. A resume only tightens the checkpoint's options and continues the same active-time budget; a caller may list sensitive paths it cannot supply (`omitSensitivePaths`).
47. The TypeSafe defaults follow the Jev constraints of section 8A: 30000 bytes, 60 options, every question rotated, response model checked, retry evidence recorded per attempt.
48. `region` is part of the element signature and identical twins report `twins`; cross-snapshot matches need both. Rejected: a signature without region (identical buttons in product cards would collide and shift).

## 16. Known risks

1. First-option bias and saturated confidence of Jev: floors are weak guards; mitigated by NONE_APPROPRIATE, rotation for arguments, forward/reverse commitment questions and the deterministic DONE gate. Not probed live: whether order bias changes answers here, noul/score shapes, 255-option behavior, 429/529 behavior (never observed in 157 requests).
2. `goal_span` candidates come from deterministic heuristics; a goal without quoted or recognizable literals yields weak spans and usually `needs_input`. Intended: values come from inputs or quoted literals, not from model generation.
3. Large native selects: more than `candidates` (100) options are trimmed by overlap; the right option may be dropped. Surfaces as `needs_input`, never a wrong pick.
4. Open shadow DOM, iframes, canvas UIs, `contenteditable`, file inputs, date pickers that are not native inputs, drag and drop, and `multiple` selects are not supported in v1 and are not offered; they are counted in `observation.unobserved` and a block while any is present is `UNSUPPORTED_SURFACE`. A verifier is told not to treat absence as evidence, but a model can still ignore it: the count is reported in the completion record as a caveat, not enforced.
5. ARIA select (`selectAriaOption`) and the real React-controlled input path were designed or emulated in s2 but never run against a real framework tree. The M1a and M3a packets must add a real-Chromium confirmation (s2 recommendation 8) and a React-controlled input case.
6. Synthetic events are untrusted (`isTrusted:false`): pages that ignore synthetic input (some payment widgets) will report `matched:false` or no change; the outcome is honest, the task blocks.
7. `target=_blank` links open a window outside the managed document; they offer no operation. A real popup blocker interaction is unverified.
8. Jsdom limits: zero layout, no `scrollIntoView`, no `scrollingElement`/element `scrollTo`, no real submit. Executor and host tests must stub layout and scrolling (s3 `domHarness.ts` is validated); behavior that depends on real layout (obscuring, geometry, smooth scroll) is only confirmed in the Chromium runs.
9. The playwright expected Chromium revision (1217) is not installed; the harness must pass `executablePath`. The machine is shared and saturated (load 34-47): at most 2 live contexts, Jev concurrency 3.
10. `dist/` is shared and rebuilt by others; only the gate packet builds. e2e must read the UMD once and record sha256, exit code 3 when exports are missing.
11. `prettier --check .` can be red on local, untracked evidence files that are not part of the change; do not reformat them. Every file a packet creates must pass `prettier --check` individually. `e2e/evidence/` must be added to `.prettierignore`. e2e is scanned as production by security-check and gitleaks: no unquoted `password|secret|token|api_key: '<16+ chars>'` literals, no lowercase `bearer <20+>`, no `sk-` + 20 alphanumerics (the id rule in section 0 prevents `task-` ids).
12. Terser strips every `console` call from the bundles: nothing may rely on console output at runtime, and debug masking tests must spy before the build.
13. Timeouts leave synchronous handlers running: after `commit()` cancellation is cooperative only; that is why the effect is `uncertain`, never `none`.
14. A model that returns a choice that was not offered is rejected, but a model that consistently picks a wrong offered target is not detected until the observed state disagrees; the DONE gate, postconditions and the caller `TaskVerifier` are the safety net, plus `maxNoProgress`.
15. The structural commit hints cover submitters, implicit-submit fields and the opt-in `data-kriya-commit` marker, on every operation. A plain `button` that purchases through script, a link whose GET deletes and a persisted switch are caught only by the classifier (stage 3, fail closed when absent) or a caller `classify` hook or `promoteEffects`. A caller who needs hard guarantees sets no grants (default), a policy `classify` hook for their app, `promoteEffects`, or restricts `authorization.operations`.
16. `AutomationEngine._validateAction` and `_withTimeout` still throw/reject inside the existing classes; the repaired `executeAction` must convert every path into a result (validation currently rejects). Callers that relied on the rejection need a CHANGELOG note.
17. The legacy `fillForm`/`submitForm` path is never used by the agent (React-controlled native inputs are not updated by it; `submitForm` can hang or hit the wrong form).
18. Evidence relies on exact-value scans: a secret transformed by the page (masked, truncated, re-encoded) is not caught. The redactor's variants (11.3) cover only the listed transformations.
19. The approval context digest includes non-sensitive field values and notices; benign page changes (a clock, a rotating banner) void an approval and cause a second ask. That is the safe direction; the cost is an extra pause.
20. A sensitive value typed under an explicit `bind` into a field that is not structurally sensitive is only as protected as the caller's redactor knowledge (the value is scrubbed everywhere the library controls, and the page can still read the field). Warning `SENSITIVE_UNCLASSIFIED_FIELD` marks the case.
21. A realm lost mid-call is resolved by transition as `applied`: an inference. If the page navigated for another reason before the activation ran, the verifier sees a state that does not match the goal and rejects DONE; the entry's resolution `transition` is disclosed in `completion.resolvedUncertain` so a caller can audit it.
22. The isolated-world deployment of the bridge needs CDP or an extension; the Playwright init script runs in the main world, where a page script that executes before it can pre-define the global (the install then fails and the run cannot proceed, which is the safe outcome) or tamper with `Function.prototype`-level built-ins. Captured built-ins reduce, not remove, that exposure.
23. The agent's consumed-approval set and checkpoint registry live in memory: a process restart forgets them. Cross-process safety needs `checkpointKey` and the `consumeApproval` hook backed by a store.
24. `includePageText` defaults to true because passages are READ elements anyway; turning it off removes only the aggregate text blob.

25. Input-driven selection for SENSITIVE inputs (a card expiry month in a native select) is not supported in v1: the model cannot see the value, and matching in code needs a materialization path that does not exist. The run returns `needs_input`, never a wrong pick. Non-sensitive input-driven selects work because the model sees the preview and chooses an observed option.
26. There is no observed-value source (copy a value shown on the page into a field); a declared resolver is the way until a binding model for page-controlled text exists.
27. An informational goal that needs a value rather than YES or NO returns the cited passages in `completion.evidence`; no extracted-value field exists because producing one would be generated text.
28. An accessible-name flip (a switch whose label changes with its state) changes the element signature: its postcondition is `absent_violated` without a later effect and `retired` (`later_effect`) with one. It is reported either way.
29. The default authorization is deliberate: every operation the host reports, on the start origin only. A read-only run uses `TASK_RESEARCH_PROFILE` or `authorization.operations`.
30. Every numeric default (floors, durations, budgets, `TASK_LIMITS`, TypeSafe defaults) is provisional until M4 records live evidence (D5).
31. Identical twins in the same region keep `.n`; across snapshots they fail closed (void or absent), so a page that inserts an identical twin between pause and resume costs one extra approval.
32. `agent.ts` comments cite `docs/task-agent-contract.md`, which M5b creates; until M5b lands the path dangles, by design and by one packet's work.
33. The `ActionType` and `ErrorCode` unions are widened, `rescript/Kriya.res` and `dist/` typings are stale until M5b and the final gate, and `executeAction` now returns results where the legacy path rejected: the migration text is an M5b deliverable.

Post-audit risks (added by the orchestrator, numbering continues after the table above):

- Cap before scrub: `TaskElementState.value` (500 chars), `TaskElement.label` (160), passages (1000) and `observation.text` (6000) are capped by the host before the coordinator's exact-match scrub, so a secret longer than a cap, or one echoed across the cap boundary, can leave an unscrubbed prefix. It needs an explicit caller `bind` of a sensitive input into a control that is not structurally sensitive, or a page that echoes the secret. Mitigation: structurally sensitive fields never carry a value at all; M3a must cap AFTER redaction wherever it already holds the secret candidates; the residual is documented, not hidden.
- A sensitive input of 1 to 3 characters (CVC, PIN) that also occurs in `TaskRequest.goal` is only a warning (`SHORT_SENSITIVE_INPUT`); the goal is never scrubbed and reaches every decider call. Callers must not put secrets in the goal.
- Numeric defaults remain provisional under D5. The recorded recovery profiles use per-run options; current defaults and evidence are qualified in the salvage reconciliation below.

## Salvage reconciliation (4 October 2026)

The implementation and authoritative types include these explicit refinements to the earlier notes:

- `TaskExpectedState.observed?: string | boolean` carries a diverged, non-sensitive actual value through the completion request. Sensitive actual values remain opaque. This closes the type/projection mismatch with section 7.3.
- Element signatures additionally hash a private security identity: resolved raw href, form action/method, submitter destination and structural commitment hints. Only the SHA prefix leaves the observer. A token change in a redacted destination therefore invalidates an old approval. Ordinary editable values, checked state, geometry and focus remain outside this identity. Immutable checkbox/radio values and pressed-button symbolic values are privately hashed.
- Checkpoints carrying caller `priorEffects` require the issuing instance, including when signed with a checkpoint key. The serialized request schema has no prior-effect slot; another process rejects such a continuation. Ordinary keyed checkpoints remain supported with durable approval consumption.
- The existing `maxOptions` clamp is 12..255. Its documentation now states that range; the default remains 60.
- Native buttons with explicit switch/checkbox/radio/option roles expose their ARIA control semantics. Native submit semantics take precedence. Label-controlled native inputs retain commitment markers on both the label and effective input.
- Coordinator redaction preserves typed identity and enum fields and scrubs textual data. Page text retains its 6000-character cap; passages, notices and validation retain their 1000-character cap. Label caps are not applied to those larger surfaces.

The e2e harness explicitly requests `expect.answer: false` for state-change scenarios and privately rebinds retained sensitive inputs when resuming. This does not change the section 7.2 distinction between absent, true and false answer expectations. Its optional confidence and offscreen profile is recorded with each run; library defaults are unchanged. Current implementation and live proof are recorded in [task-agent-status.md](task-agent-status.md).

## Continuation refinements (4 October 2026)

- A rejected decision excludes only a known `(operation, signature)`. A missing or foreign target does not exclude every target of an operation. Existing budgets still bound repeated rejected decisions; uncertain executions retain their run-wide exclusions.
- Action-request trimming retains modal controls, then controls with offered operations other than READ, then viewport and passive content. This prevents visible passages from displacing a needed control outside the viewport. Argument and completion request priorities remain unchanged. `TaskModelElement.expanded` and target criteria preserve the observer's expansion state, including in value-free commitment requests.
- `computeOffers` withholds SUBMIT for active native invalid constraints. Native constraints disabled by `novalidate` do not trigger this preflight; explicit application errors remain model evidence. `compileCommand` returns `FORM_INVALID` for SUBMIT or Enter in such a form, before classification and approval. This is a browser-state preflight; it does not claim that server validation will succeed.
- The full DONE gate additionally returns `PERSISTENCE_NOT_VERIFIED` when a lasting commitment other than standalone `form_submit` has occurred and a prior changed control of that commitment's form remains in the writing document. A same-document matching control and any success message remain local evidence. An authoritative caller verifier returning SATISFIED clears this persistence failure, but never bypasses the model, evidence or other gate checks. A later document with matching controls also clears this failure and must pass the existing postcondition checks. Same-document flows with no independent confirmation can therefore stop even after a successful write. This guard does not authenticate page records or replace an application verifier.

The latest evidence is qualified in [task-agent-status.md](task-agent-status.md). These refinements change no goal, route, selector, scenario assertion, confidence default or authorization grant.
